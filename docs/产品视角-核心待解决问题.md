# Job Lens 产品视角核心待解决问题

> 记录时间：2026-08-18
> 当前状态：项目开发暂停；以下问题作为恢复开发前的产品阻塞清单，不代表已经完成修复。

## 结论摘要

当前项目已经具备“公开索引采集 → 统一数据合同 → 岗位卡片 → 决策状态”的基础链路，但还不能稳定地产出“可持续、有效、可行动”的岗位池。主要风险集中在采集能力、岗位有效性、证据完整性和人工复核入口四个方面。

## P0：采集与复核链路阻塞

### 1. OCR/评分链路无法启动

- 现象：`ocr-score` 依赖 Chrome 插件/浏览器采集能力，当前插件无法安装，导致截图获取、OCR、评分链路无法正常开始。
- 产品影响：岗位只能停留在 `public_index / unverified_index_snapshot`，无法升级为完整 JD 证据；匹配分数和推荐结论不能可靠生成。
- 待解决方向：提供不依赖插件安装的采集入口（浏览器内置能力、手动截图导入或受控文件导入），并明确 OCR 输入、失败重试、同一岗位升级和证据降级规则。
- 恢复条件：能对单个岗位完成“截图/文本输入 → OCR → 字段提取 → 评分 → 可追溯证据”的端到端验收。

### 2. Public-index 无法持续获得新的具体岗位

- 现象：历史库已有约 408 个稳定岗位 ID；最近可验证的一轮公开检索返回 12 个原始结果，其中 7 个是列表页、5 个重复，新增具体 `job_detail` 为 0。
- 运行层问题：后台状态曾长时间不更新；Codex CLI 还受到运行目录只读、网络/DNS 和非交互执行环境影响。即使 CLI 成功启动，搜索结果也可能只有列表页而没有新的详情链接。
- 产品影响：岗位池无法达到目标规模，自动化会出现“任务运行但岗位数量不增长”的假象。
- 待解决方向：扩大并轮换查询矩阵（岗位方向、地区、公司、行业、时间词），区分“列表发现”和“可入库详情”，增加搜索覆盖率与边际收益指标；同时保证每轮状态可观测。
- 恢复条件：连续多轮能够稳定产生新的、可去重的岗位 ID，且 `accepted_new / duplicates / discovery_pages / rejected` 可解释。

### 3. 缺少已关闭岗位筛选，历史岗位有效性不足

- 现象：公开索引通常无法确认岗位当前开放状态；历史采集结果中曾出现大量岗位已关闭或失效。
- 产品影响：岗位池规模看似增长，但用户点击后可能无法投递，降低信任和使用价值；“新增岗位数”不能直接等同于“有效机会数”。
- 待解决方向：增加岗位生命周期字段和筛选层级：`unknown`、`open`、`closed`、`expired`；将详情页/列表页重新检查、用户点击结果、明确关闭文案分别作为不同强度的关闭证据；默认隐藏已确认关闭岗位，并单独展示待复核岗位。
- 恢复条件：站点支持按有效状态筛选，关闭状态有证据来源和时间，且未知状态不会被误判为开放。

## P1：信息完整性与决策质量

### 4. 核心公司和岗位字段缺失

- 典型缺失：公司融资阶段、公司规模、行业、办公地点、招聘者信息、岗位开放状态、完整 JD、发布时间等。
- 产品影响：用户无法判断公司质量、岗位真实性、机会优先级；评分容易退化成标题/摘要匹配，无法支撑投递决策。
- 待解决方向：建立字段完整率指标和分层信息模型：
  - 必填：标题、公司、城市、具体岗位链接、来源证据；
  - 重要：薪资、经验、学历、职责摘要、开放状态；
  - 增强：融资阶段、规模、行业、招聘者、发布时间。
  对缺失字段明确显示“未知/待验证”，禁止推断填充；允许 OCR 或人工复核按稳定 ID 增量补全。
- 恢复条件：岗位卡片展示字段完整率；关键字段缺失时推荐结论保持“信息不足”，而不是给出虚假的高分。

## P1：采集到站点的闭环可靠性

### 5. 数据状态、站点发布和自动化状态不一致

- 现象：历史上出现过自动化任务显示运行，但 `worker-state` 长时间不更新、没有锁/PID，或者任务只完成检索而未完成站点导入。
- 产品影响：用户无法判断“采集成功”“站点已更新”和“只是发现证据”之间的区别。
- 待解决方向：每轮统一记录：采集开始/结束、原始结果、稳定 ID 新增、重复、拒绝、待复核、数据校验、构建、部署和站点新增数；任何一步失败都保留旧站点并明确失败原因。
- 恢复条件：从一次轮次状态可以完整回答“采集了什么、收录了多少、为什么没收录、站点是否已更新”。

## 本次巡检新增发现

### 6. 历史库、站点库和有效岗位口径不一致

- 当前 `outputs/boss-index-history.json` 有 408 条，`data/jobs.json` 只有 357 条，差异 51 条。
- 差异记录多数来自旧采集格式或标题不符合当前“产品经理”入站规则，但仍留在历史库中；目前没有清晰的“已归档/被过滤/待清洗”状态。
- 产品影响：用户看到的岗位总数、采集累计数和站点展示数无法直接对账。
- 待解决方向：建立统一岗位生命周期和数据状态：`discovered`、`accepted`、`quarantined`、`closed`、`expired`；每次转换输出过滤原因和对账报告。

### 7. 自动化状态与真实运行状态可能脱节

- 当前任务可以显示为运行，但 `worker-state` 长时间不更新，且没有锁/PID/日志可供判断是否真的执行。
- 产品影响：无法区分“等待下一轮”“CLI 失败”“搜索无结果”和“任务已经停止”。
- 待解决方向：增加心跳时间、当前批次阶段、错误码、连续无新增次数、最后成功部署时间；状态机至少区分 `running`、`blocked`、`paused_no_new`、`batch_failed`、`target_reached`。

### 8. 站点发布结果不可验证

- 项目有 Sites `project_id`，但当前没有稳定可见的部署 URL、部署版本和 `site_import_new` 证据链。
- 产品影响：无法确认岗位数据是否已经落到用户实际访问的站点，也无法回滚到上一版数据。
- 待解决方向：记录部署 URL、部署 ID/提交版本、岗位数据版本、发布时间和回滚入口；部署失败时明确保持旧版本。

### 9. 质量门禁与当前数据基线不一致

- `validate:data` 当前通过，但完整渲染测试仍按 322 条旧基线断言，而站点数据已有 357 条，导致 `pnpm test` 失败。
- 产品影响：测试结果不能直接作为发布信号，团队无法判断是数据更新还是代码回归。
- 待解决方向：将岗位数量改为由固定 fixture 或数据版本驱动；把“数据快照变化”和“代码行为回归”拆成两类测试。

### 10. 数据合同存在双层字段命名，迁移成本高

- 历史采集记录使用 `job_title/company_name/job_url`，站点合同使用 `title/company/url`；转换脚本承担了大量兼容逻辑。
- 产品影响：新字段容易只写入一层，造成岗位卡片或评分链路看不到信息；字段完整率也难以统一计算。
- 待解决方向：明确唯一规范合同，采集、OCR、整合、站点只在边界处做一次适配，并为旧数据提供版本化迁移和失败隔离。

### 11. 岗位有效性和新鲜度没有成为用户可见指标

- 当前岗位卡片能显示验证状态，但没有明确显示“最后索引时间”“最近一次复核时间”“是否可能已失效”。
- 产品影响：用户无法判断一条公开索引岗位是否值得立即点击或投递。
- 待解决方向：增加 `observed_at`、`last_verified_at`、`freshness` 和有效性筛选；超过阈值自动降为待复核，而不是继续当作普通岗位展示。

### 12. 个人决策状态与数据版本缺少冲突提示

- Workbench 会按稳定岗位 ID 保存个人状态，这是正确的；但岗位被替换、归档或重新采集后，用户不一定能看到“岗位证据已变化”。
- 产品影响：用户可能基于旧摘要继续保留候选状态，产生决策滞后。
- 待解决方向：保存数据集版本和岗位 `last_seen_at`；岗位证据发生变化时提示用户重新确认，不直接覆盖个人状态。

## 恢复开发时的建议顺序

1. 先恢复 Codex CLI/浏览器运行环境和自动化可观测性，确保采集轮次真实执行。
2. 再补 public-index 的搜索覆盖与岗位有效状态模型，避免继续堆积失效岗位。
3. 同步完善字段完整率、公司信息补全和证据来源展示。
4. 最后打通 OCR/评分，使用已能稳定复核的岗位做端到端验收。

## 暂不纳入本阶段的事项

- 不把未验证公开索引直接当作完整 JD 或高置信推荐。
- 不绕过 BOSS 登录、验证码或安全页。
- 不在没有明确证据时推断融资阶段、开放状态或评分。
